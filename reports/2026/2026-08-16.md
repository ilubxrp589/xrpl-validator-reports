## Engineering changes

- **fix(xrpl-ledger): AccountDelete walks the owner DIRECTORY — OwnerCount 0 is not "owns nothing"** (`a31296a`, xrpl-validator)
  Our only gate was `OwnerCount == 0`. #106322004 77C5E61D has OwnerCount 0 AND owns an Escrow, and those are not contradictory: an escrow that names this account as DESTINATION is linked into its owner directory, but the reserve sits with the escrow's CREATOR, so the destination's count never moves. The count says "owns nothing" while the directory says otherwise.
- **fix(xrpl-ledger): NFTokenBurn takes the token's OUTSTANDING OFFERS with it** (`1559d5f`, xrpl-validator)
  We removed the token from its page and bumped BurnedNFTokens, and stopped — leaving offers pointing at an NFT that no longer exists. `NFTokenBurn::doApply` deletes up to 500, SELL directory first: std::size_t const deletedSellOffers = nft::removeTokenOffersWithLimit( view(), keylet::nftSells(id), kMaxDeletableTokenOfferEntries); if (kMaxDeletableTokenOfferEntries > deletedSellOffers) …
- **fix(xrpl-ledger): a rested XRP residual rounds by mulRound, not by a plain ceiling** (`a8b01c7`, xrpl-validator)
  The bookend to `ff1e752`. There, `TOffer::limitOut` uses `ceilOutStrict` and gets a TRUE ceiling. Here, `flowCross`'s residual uses plain `mulRound`: afterCross.in = mulRound(afterCross.out, rate, takerAmount.in.asset(), true);
- **feat(node): S3 — a proposal's tx-set hash is a SHAMap root, not a concatenation** (`43fdc99`, xrpl-validator)
  `compute_tx_set_hash` was a placeholder: sort the ids, concatenate, SHA512Half once. That shares no structure with a SHAMap, so every proposal we generated named a set hash no peer could ever agree with. Harmless so far only because nothing consumes it yet — M2a is where it would have started mattering.
