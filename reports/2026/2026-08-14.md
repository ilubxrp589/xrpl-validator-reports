- **fix(xrpl-ledger): measure the REVERSE pass's consumption precisely too** (`45a7092`, xrpl-validator)
  `44c20d9` fixed the forward carry and I did not notice the same defect one level up. `measure_hop` worked out how much a trial consumed by differencing a GRANTED balance — 16 significant digits TOTAL, so the grant itself eats the low end of the answer — while `cross_engine_to` was already RETURNING the precise remaining input and the code threw it away with `let (rw, _, _) = ...`.
- **fix(xrpl-ledger): the precise measurement must account for the fee the walk debits** (`1f31546`, xrpl-validator)
  A defect in `45a7092`. Its precise path is `granted - rem_in`, but `rem_in` tracks only the NET the walk moved — the input transfer fee is debited SEPARATELY by `line_adjust`. So on a fee-bearing hop `precise` is the net while the differenced balance `d` is the gross, the two disagree by the WHOLE FEE (1e-3 for a 1.001 issuer, a thousand times the 1e-9 agreement threshold), and the guard rejected the precise value …
- **fix(xrpl-ledger): ask the walk what a strand spent, don't difference the balance** (`8d8d2e6`, xrpl-validator)
  Third instance of the defect `44c20d9` fixed for a hop's carry and `45a7092` for the reverse pass — and exactly the `signed_add(before, !after)` shape 45a7092's note said to go looking for. `strand_pass` reported its input consumption by differencing the sender's spend-leg balance, and a balance holds 16 significant digits TOTAL, so whatever the sender already holds of the spend currency eats the low end of the …
- **feat(xrpl-ledger): one AMM consumption per payment-engine iteration** (`4566c4e`, xrpl-validator)
  "At any payment engine iteration, AMM offer can only be consumed once" (BookStep.cpp:818). When a payment wants more pool liquidity than one AMM offer gives, rippled ENDS the pass and `flow()` re-enters the strand for the next one — and every iteration writes the maker's residual, so N iterations are N roundings. We took Fibonacci slices inside a single pass and rounded once.
- **fix(xrpl-ledger): the bridge's direct head prices a partial fill at the filed rate** (`7f8286b`, xrpl-validator)
  The rule `e2a9c99` gave the two bridge legs, never given to the third fill site in the same function. An offer carries two rates: the one it is FILED under (low 64 bits of `BookDirectory`, a 16-digit mantissa fixed at creation) and its current TakerPays/TakerGets, which drifts every time a residual is re-rounded. rippled prices a PARTIAL fill at the filed rate and a FULL one at the amounts.
- **fix(xrpl-ledger): limitOut takes the STRICT canonicaliser when the drops decide** (`ff1e752`, xrpl-validator)
  rippled's own comment on `TOffer::limitOut` (Offer.h:200): "It turns out that the ceil_out implementation has some slop in it, which ceil_out_strict removes." So an out-limited fill goes `ceilOutStrict` -> `mulRoundStrict` -> `canonicalizeRoundStrict`, not `mulRound`. After dividing down to offset -1 the two differ by one term (STAmount.cpp:1477 vs :1516): canonicalizeRound value += 9; canonicalizeRoundStrict value …
- **fix(xrpl-ledger): rippleSend moves the sender's line ONCE, with the gross** (`bc756dd`, xrpl-validator)
  rippled's `rippleSend` (View.cpp) is one credit per party: saActual = saAmount + saTransitFee; rippleCredit(issuer, receiver, saAmount); // receiver gets the NET rippleCredit(sender, issuer, saActual); // sender pays the GROSS
- **fix(xrpl-ledger): every payment strand runs ONE PASS — corpus byte parity 0 hits** (`950e63e`, xrpl-validator)
  The third and last part of the iteration model, and the SAME `if multi` gate the rounds carried in `4566c4e`. A pass ends when an offer is CONSUMED and `flow()` re-enters the strand; `single_pass` already implements that, but it was switched on only for multi-strand payments, so a lone strand walked the whole book in one call and MERGED what rippled does in separate iterations.
- **fix(xrpl-ledger): NFTokenAcceptOffer weighs the buyer's funds — and the probe lets it see them** (`9c0d845`, xrpl-validator)
