- **fix: LedgerHashes sub-page key computed dynamically (seq/65536)** (`cd280e4`, xrpl-validator)
  The XRPL state tree has a LedgerHashes sub-page that changes every ledger (new hash appended). Key = SHA512Half(0x0073 || uint32_be(seq/65536)). This object was never in AffectedNodes and wasn't being fetched, causing a persistent 32-byte drift after ~30-200 ledgers.
- **perf: branch-cached hash computation + skip second download** (`71c6f35`, xrpl-validator)
  - Cache 16 root-level branch hashes, only recompute dirty branches - Fast path now marks dirty branches (was the cause of optimized-mode drift) - Skip second download entirely — ws_sync starts from pinned ledger - Skip-ahead when >50 ledgers behind (prevents rippled pruning stalls) - Dynamic LedgerHashes sub-page key: SHA512Half(0x0073 || seq/65536)
- **perf: single-pass merge + spawn_blocking — every ledger verified, feed stays smooth** (`5cf2901`, xrpl-validator)
  - Replace O(k*n) Vec inserts with O(n) single-pass merge: update drops from 6-9s to 0.4s - Total hash time 2.8s — under the 3.5s ledger interval, now verifying every ledger - Move update_and_hash to spawn_blocking: SSE feed, peers, and web UI no longer freeze - Faster metadata retry bail-out: 3 attempts then break batch (prevents stale-ledger stall) - Partial failure tolerance: apply successful fetches even if some …
