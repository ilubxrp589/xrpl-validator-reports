## Findings fixed

- **fix(ledger): F399 — two-asset AMM withdrawals check the reserve before each new trust line (soak #28 receipt)** (`ea76860`, xrpl-validator)
  rippled's `AMMWithdraw::withdraw()` runs `sufficientReserve` for each asset right before its send, in every withdrawal mode (AMMWithdraw.cpp 765/785): a withdrawal that would create a trust line for an account owning two or more objects needs base + increment x (OwnerCount + 1) against the balance before the fee. The single-asset paths had this check (finding 156); the two-asset equal withdrawals (tfWithdrawAll and …
- **fix(ledger): F400 — NFT IOU settlement grosses the transfer fee to nearest, as accountSend does (soak #28 receipt)** (`a08b8ee`, xrpl-validator)
  An NFTokenAcceptOffer settles in an IOU with rippled's `pay()` = `accountSend`, whose third-party send grosses the sender's debit with `multiply(saAmount, transferRate)` (TokenHelpers.cpp:869): STAmount multiply, `Number{v1} * Number{v2}`, rounded to the NEAREST 16-digit value. The engine used `gross_in`, the payment engine's round-up `mulRatio` (correct for BookStep, not for accountSend).

## Notes

_Hand-written notes on the day's XRPL work: research and operations._

- **Warm restart (merged, not yet deployed).** Every deployment has restarted the node from an empty store and
  re-downloaded the full ledger state (about 19.9 million objects), so it resumed 90–111 ledgers behind the network.
  The node can now resume from its own saved state instead: a clean stop parks the ledger-sync loop between ledgers and
  records the last verified ledger; on restart the node checks that its stored state names that ledger, rebuilds the
  state tree and requires its root to equal the network's account hash for that ledger before continuing. Any doubt
  falls back to the full resynchronisation. Earlier attempts to restart without resynchronising (April and August)
  failed because they resumed from the wrong ledger; this design verifies the ledger first. A rehearsal on two real
  mainnet states kept from the 2026-09-23 deployments rebuilt both to the network's account hash (31–34 s each). The
  first deployment that carries this code still starts cold; the one after it is the first warm restart.
- **Soak #28 receipt and finding F399.** At ledger 107,210,679 an AMMWithdraw (withdraw all, from a BTC/xSPECTAR pool)
  came from an account holding 2.799986 XRP at an owner count of 9 with no trust line for either pool asset. rippled
  checks the reserve for each new trust line before paying each asset out, in every withdrawal mode; a new line at that
  owner count needs 3 XRP, so mainnet returned `tecINSUFFICIENT_RESERVE`. The engine's two-asset withdrawal paths
  (withdraw all, and withdrawal by LP-token amount) skipped that check and paid both assets out. Fixed (F399) with the
  mainnet transaction pinned as a regression vector; verified and merged; deployment awaits a decision.
- **Operations.** At 01:40–01:55 EDT a test build on the machine that runs the reference rippled node pushed it into
  memory pressure; its validated ledger fell about ten minutes behind and the live node paused until it recovered
  (no mismatches, no engine receipts). Full test batteries no longer run on that machine while the live node depends on it.
- **Second soak #28 receipt and finding F400.** At ledger 107,211,701 an NFTokenAcceptOffer settled a buy offer priced
  211,299.047746283 SOLO; the SOLO issuer charges a 0.01% transfer fee, so the buyer's debit is the price times 1.0001.
  rippled grosses that debit with its standard amount multiplication, rounded to the nearest 16-digit value
  (211,320.1776510576); the engine used the payment engine's round-up rule for the same product (…0577), leaving the
  buyer's SOLO balance one unit lower in the sixteenth digit. Earlier NFT sales with a transfer fee had exact products
  and could not show the difference. Fixed (F400) with the mainnet transaction pinned as a regression vector; verified
  and merged; deployment awaits a decision.
- **Deployment (F398–F400 and the warm restart).** Build a08b8ee replaced the live shadow build at 18:58 EDT after its
  gate (1,621 suite tests and 707 flow-engine tests passing) and both mainnet replay windows (60 and 98 ledgers, zero
  mismatches). This deployment still started from a full resynchronisation, as designed (the previous build could not
  leave a resume ticket). The health check matched 408 ledgers with no mismatches, and soak #29 began at 19:26 EDT (seed
  ledger 107,213,499). The receipt canary confirmed the comparison is live on the new build.
- **Build infrastructure.** Test gates now run on a dedicated build machine instead of the machine that hosts the
  reference rippled node, whose disk the test builds had been saturating. The gate completed in 10 minutes (previously
  about 15) with no effect on the reference node.
