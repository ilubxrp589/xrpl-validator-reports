## Engine findings fixed

- **fix(xrpl-ledger): F291 — a crossing's remainder is re-derived from the sorted fold before `done` is believed** (`5422429`, xrpl-validator)
  rippled recomputes remainingOut at every iteration boundary as `outReq - sum(savedOuts)` over the ASCENDING multiset (StrandFlow.h:791); the running chain is never consulted. Ten consecutive tecKILLED receipts (107044846-857, rGH4WSUU's Fill-or-Kill RLUSD buys) had four iterations whose chain decrements to exactly zero while the sorted 16-digit fold is 45.66475799999999 against 45.664758 wanted: a 1e-14 crumb. …
- **fix(xrpl-ledger): F292 — under FlowSortStrands a strand behind the iteration's winner is not flowed, so it reaps nothing** (`7bd0c74`, xrpl-validator)
  rippled flows an iteration's admitted strands in bound order and breaks at the first that succeeds and passes limitQuality (StrandFlow.h: `best.emplace(...); pushRemainingCurToNext(strandIndex + 1); break;`). The strands behind the winner are not flowed that iteration: no rev pass, no offer stream, nothing reaped.

## Engineering changes

- **feat(xrpl-ledger): TxFields::from_json, inner_batch flag and the Batch tem codes** (`46825c1`, xrpl-validator)
  Add `TxFields::inner_batch: bool` plus `fee_missing()` (waived for batch inners) and `from_json()`, moved from xrpl-node's native_apply::build_txfields (now a one-line delegate). from_json decodes the Account field via tx::offer::decode20, which accepts the engine's hex account dialect as well as base58 — build_txfields's original decode_address call was base58-only and could not read the hex Account strings the …
- **feat(xrpl-ledger): the fee-zero preflight gate is fee_missing(), waived for batch inners** (`6b5a309`, xrpl-validator)
- **feat(xrpl-ledger): apply_on_sandbox — the tx pipeline on an existing sandbox with rollback** (`99c4e14`, xrpl-validator)
  Mirrors xrpl_node::native_apply::native_apply_one but runs on a caller-supplied Sandbox instead of allocating a fresh one, restoring the entry snapshot on every non-applied path and keeping only the common changes on a claimed tec. Task 4 will call this per inner transaction of a Batch.
- **feat(xrpl-ledger): BatchTransactor — preflight, signer set, fee formula, and the four-mode inner loop** (`20af7bd`, xrpl-validator)
- **fix(xrpl-ledger): BatchTransactor — rippled 3.3.0 result codes, single-inner rejection, signer cap, cleared inner results** (`05be0f5`, xrpl-validator)
- **feat(xrpl-node): the native shadow skips Batch inner entries and attributes them to their outer** (`bd7b2c3`, xrpl-validator)
  rippled records every Batch (BatchV1_1) inner transaction as its own ledger entry — own hash, own metadata carrying ParentBatchID, the indices right after its outer — but APPLIES it inside the outer's application. Our BatchTransactor::do_apply does the same, so the shadow's replay must skip the inner entries and compare the outer's mutation set against the union of the outer's and its inners' AffectedNodes.
- **fix(xrpl-ledger): BatchTransactor decodes base58 and hex accounts alike (decode20)** (`07e7a11`, xrpl-validator)
  `decode_account` accepted only the 40-hex-char dialect, on the assumption that `native_apply::hexify_addresses` had already rewritten every r-address in the transaction. It has not: that pass runs on ledger-state pre-images, and `TxFields::from_json` only rewrites the outer's own top-level account fields — nested `RawTransaction`/`BatchSigner` objects keep whatever dialect the feed sent. Every real Batch therefore …
- **feat(xrpl-ledger): per-inner threading for Batch — touched-key tracking and stamp_batch_threading** (`4c116ab`, xrpl-validator)
  rippled applies every Batch inner as its own transaction (`applyBatchTransactions` -> `apply(..., inner, tapBATCH)`), so each ledger object an inner touched threads the INNER's transaction id, while the outer's own changes (its fee and sequence) thread the outer's. The last toucher wins. Our engine runs the inners inside the outer's `do_apply` and the callers stamped the whole mutation set with the outer's hash, …
- **fix(xrpl-node): batch_vector harness warning; threadOwners coverage and a fallback receipt for the batch stamp** (`c13f4c8`, xrpl-validator)
  `assert_expect` took a `&LedgerState` it never read, which the test target reported as `unused variable: state` — the parameter is gone from the signature and both call sites (the earlier clippy sweep never linted the file: it exits on the pre-existing errors in xrpl-ledger before reaching the node's test targets).
- **feat(xrpl-node): Batch attribution and per-inner threading in the replay tools' native legs** (`90453a6`, xrpl-validator)
  state_replay and differential_probe iterate a ledger's entries the same way the native shadow does, and both were still applying Batch INNER entries standalone — which the engine rejects out of hand (tfInnerBatchTxn with Fee "0") — and stamping the outer's mutations with the outer's hash alone. Every Batch ledger therefore read as a divergence on every inner and a threading byte-diff on the outer.
- **fix(xrpl-node): differential_probe — guard the inner-result zip and print inner_ter in the text report** (`e5fbfb0`, xrpl-validator)
  The kept inner ids are the ones the FIXTURE carries; the per-inner results are the inners the engine ATTEMPTED. Pairing them by index is meaningful only while the two lists agree — one hole shifts every later inner onto its neighbour's result and reports a confident, wrong verdict. The per-index comparison is now guarded by a length check; on disagreement it withholds the inner verdicts, prints one BATCH-INNER …
