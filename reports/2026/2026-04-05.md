  The ffi_test server now fetches every new mainnet ledger from rippled and runs each tx through libxrpl's parse + preflight via our FFI.
- **feat(ffi): full apply() on live mainnet tx with RPC-fetched state** (`7d0acd7`, xrpl-validator)
  Every few seconds, we sample ~3 txs per new mainnet ledger and run them through libxrpl's FULL apply() via FFI. SLE lookups happen synchronously via rippled's ledger_entry RPC (pre-ledger state at seq-1).
- **feat(ffi): 100% mainnet agreement — libxrpl apply in full** (`0f7682f`, xrpl-validator)
  Three root causes fixed to hit 100% tx-result agreement with mainnet on live feed, up from 55%: 1. Overlay tombstones (LayeredProvider) Deleted SLEs were `remove()`-ed from overlay, so the next lookup fell through to RPC which returned the stale *pre-ledger* version. Now we insert `None` as a tombstone so the fallback is bypassed. Killed OfferCancel/tefBAD_LEDGER (36→0). 55% → 82%.
- **feat(ffi): production observability — Prometheus, Grafana, SLOs** (`00b54ca`, xrpl-validator)
  Ripple-grade metrics stack around the 100% agreement guarantee: - OpenMetrics /metrics endpoint on port 3778 exposing: * xrpl_ffi_mainnet_agreement_ratio (gauge, SLO target = 1.0) * xrpl_ffi_apply_total{result=tesSUCCESS|tec_claimed|diverged} * xrpl_ffi_apply_duration_seconds histogram (p50/p95/p99) * xrpl_ffi_apply_ter_total{ter}, xrpl_ffi_apply_by_type_total{tx_type} * xrpl_ffi_diverged_total{tx_type,ter} * …
- **fix(ffi): retry + failover against rippled overload** (`9993061`, xrpl-validator)
  Root cause of 97.26% agreement drop: rippled under memory/load pressure returns plain-text "Server is overloaded" responses (not JSON errors). RpcProvider was parsing these as "no node_binary found" and returning None, which libxrpl interpreted as "this SLE doesn't exist" → terNO_ACCOUNT for accounts that definitely exist on mainnet.
- **refactor(validator): tx_engine → FfiVerifier (libxrpl via FFI)** (`5c0eef0`, xrpl-validator)
  Replace the 1164-line pure-Rust tx_engine verifier with FfiVerifier, which replays each ledger's tx set through libxrpl (rippled's C++ engine) and tracks mainnet agreement via the same infrastructure ffi_test uses. Deletes tx_engine.rs outright.
- **feat(ffi): Stage 1b — RocksDB-backed SLE provider** (`b1aad92`, xrpl-validator)
  Add OverlayedDbProvider: 3-tier lookup (in-ledger overlay → rocksdb snapshot of the validator's own state → RpcProvider fallback). Dropping RPC load from ~10 calls/tx to ~0-1 calls/tx once the validator's DB is populated.
- **fix(ffi): OwnedSnapshot eliminates verify race condition** (`0b275be`, xrpl-validator)
  The bug: Stage 1b's OverlayedDbProvider took a rocksdb snapshot inside spawn_blocking — which could run AFTER ws_sync's process_ledger wrote post-ledger state to the DB. FFI verify then saw POST-state as PRE-state, tried to insert already-existing entries into directories, and libxrpl's ApplyView hit LogicError("dirInsert: double insertion") → std::abort() → process crash.
- **fix(sync): bulk_sync rpc_failover was ignoring XRPL_RPC_URL override** (`8d1d941`, xrpl-validator)
  rpc_failover() iterated HARDCODED RPC_ENDPOINTS (localhost → xrplcluster → s1.ripple.com). On the validator host (no local rippled), this means every worker falls over to public endpoints that don't serve ledger_data, producing "DONE: 0 objects". The XRPL_RPC_URL env var only affected the initial ledger query, never the worker threads.
- **fix(ffi): disable DB snapshot during catchup — use pure RPC path** (`c2f8f6a`, xrpl-validator)
- **fix(rpc): rpc_request() was ignoring XRPL_RPC_URL env override — used hardcoded localhost** (`1fc4d55`, xrpl-validator)
