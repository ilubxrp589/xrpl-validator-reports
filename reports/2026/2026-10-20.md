## Findings fixed

- **fix(ledger): F422 — AccountDelete takes an old account's empty last directory page with its directory (ApplyView.cpp:221)** (`ca1f172`, xrpl-validator)
  rippled removes a deleted account's owner directory through ApplyView::emptyDirDelete, which also clears a case older rippled code left behind: an empty last page. When the root holds no entries and both its links name one other page that is empty too, the root's links drop to 0 and that page is erased, then the root. The engine deleted the empty root only.
- **fix(ledger): F423 — removing a directory page takes an empty last page after it, as rippled's dirRemove does (ApplyView.cpp:362)** (`53c58cf`, xrpl-validator)
  rippled's dirRemove has two branches for an empty last page that older rippled code left behind. When a page in the middle of a directory empties and the page after it is the last one and empty, that page is erased too: the previous page becomes the last, and the root points back to it. ### Other engineering changes

- **fix(validator): short of quorum here, sign the hash the reference node validated when our own hash agrees** (`e6bb9d1`, xrpl-validator)
  Since cycle 183 the validator signs a ledger only once the trusted validations reaching it reach quorum. On mainnet #107783807-814 (20 Oct) only 26 or 27 of quorum 28 reached us, so it signed none of the eight, though the reference node validated each and data.xrpl.org scores them missed.
- **feat(validator): independence 5a, sign a ledger only with our own hash of it** (`7866189`, xrpl-validator)
  Until now the validator signed the hash the trusted validators reached quorum on (cycle 183), or the reference node's when that quorum fell short here and our own hash agreed (cycle 184). Our own hash of the ledger was checked only in that second case.
- **fix(validator): while the validator's ledger feed catches up, sign the older ledgers in order, not jump to a newer quorum** (`00cce16`, xrpl-validator)
  On mainnet #107786761-772 (20 Oct) three heavy ledgers (1,001 to 1,536 transactions) and a burst of peer reconnects left the validator's ledger feed 11 ledgers behind and our tally of trusted validations short on those ledgers. The quorum on #107786773 came first, the validator signed it, and a validator cannot sign an older ledger after a newer one, so twelve went unsigned, though our own hash and the reference node's agreed on each a few seconds …
- **feat(validator): a short ledger's receipt names the trusted validators whose validations never reached us** (`3c4e4fa`, xrpl-validator)
  When fewer than a quorum of trusted validations reach us for a ledger, the receipt now lists the trusted validators (nH… keys) whose validation of that hash never arrived, those that validated another hash among them, and says whether the ledger was signed anyway.
- **feat(validator): Step 4 stage A, make the engine's inputs from a peer ledger's bytes and hold them against the reference node's** (`77e4bca`, xrpl-validator)
  Step 4 needs the engine to run on ledger data from peers, not the reference node's JSON. Stage A builds that copy and checks it live, in shadow only: the engine still runs on the reference node's inputs and peer_fetch::is_source() stays false.
